# Contributing to usecalendar

Thanks for helping. This guide covers the setup, the day-to-day workflow and what a pull request needs. The engineering standards (TypeScript, styling contract, accessibility, versioning) are in [AGENTS.md](./AGENTS.md). Please read them before a non-trivial change.

## Setup

Requirements:

- Node.js 20 or newer (CI uses Node 24).
- pnpm 12.3.4, the version pinned in `devEngines` (`corepack enable` picks it up).

```bash
git clone https://github.com/SebastianUrdaneguiBisalaya/usecalendar.git
cd usecalendar
pnpm install   # also installs the git hooks (husky)
```

## Monorepo layout

```
packages/
  core/    @usecalendar/core: framework-agnostic types and calendar math (no UI, no runtime dependencies)
    src/index.ts        the package's only public entry
    tests/              vitest, mirroring src/
  react/   @usecalendar/react: React components and hooks, built on core
    src/index.ts        → "@usecalendar/react"
    src/mini/index.ts   → "@usecalendar/react/mini" (the day strip only)
    src/styles/         theme.css (Tailwind v4 apps) and index.css (→ styles.css, apps without Tailwind)
    tests/              vitest: SSR markup tests and jsdom hook/interaction tests
```

- Only the entry files (`src/index.ts`, and `src/mini/index.ts` in React) decide the public API. Anything they don't re-export is internal and can be refactored freely.
- Logic needed by more than one framework adapter belongs in core.
- `dist/` is generated by the build and never committed.

## Scripts

Run them from the repository root. Each one runs in every package.

| Command | What it does |
|---|---|
| `pnpm run build` | Builds every package with tsup (ESM, CJS and `.d.ts`), plus the React stylesheets. |
| `pnpm run dev` | Rebuilds on change (`tsup --watch`). In `packages/react`, `pnpm run dev:css` watches `styles.css`. |
| `pnpm run typecheck` | `tsc --noEmit` in every package. |
| `pnpm run lint` | Biome lint and format check. `pnpm run lint:fix` applies fixes. |
| `pnpm run test` | Vitest in every package. `pnpm run test:watch` for watch mode. |

Tests never use a browser: no Playwright, Puppeteer or screenshot tests. React components are checked as server-rendered HTML (`react-dom/server`). Hook and interaction tests opt into jsdom with `// @vitest-environment jsdom`, and the `renderHook` helper is in `packages/react/tests/render-hook.tsx`. The UI itself is verified by hand.

## Workflow after a source change

1. Write or update tests next to the change (`tests/` mirrors `src/`).
2. Run `pnpm run lint:fix`, then `pnpm run typecheck` and `pnpm run test`.
3. If you touched packaging, entry points or styles, run `pnpm run build` and check `dist/`.
4. If the change is visible to consumers, update the README and the TSDoc of every affected export.

Git hooks run some of this for you. **pre-commit** runs Biome on the staged files. **pre-push** runs `typecheck`, `test` and `build`. The hooks are a safety net, not a substitute for running the checks.

## Trying the packed packages

Before changing packaging (entries, `exports`, tsup config) or a release, test the real tarballs in a separate project:

```bash
pnpm run build
pnpm --filter ./packages/core pack --pack-destination /tmp/usecalendar
pnpm --filter ./packages/react pack --pack-destination /tmp/usecalendar

# in another project
npm install /tmp/usecalendar/usecalendar-core-x.y.z.tgz /tmp/usecalendar/usecalendar-react-x.y.z.tgz react react-dom temporal-polyfill
```

Check that:

- `import` (ESM) and `require` (CJS) of `@usecalendar/react` and `@usecalendar/react/mini` both work.
- Types resolve in the editor and with `tsc` (`moduleResolution: "nodenext"` or `"bundler"`).
- Every `.mjs` / `.cjs` file starts with `"use client"`.
- A `CalendarLocaleProvider` imported from `@usecalendar/react` applies to a `MiniCalendar` imported from `/mini` (the entries share their React contexts).
- `@usecalendar/react/theme.css` and `@usecalendar/react/styles.css` style both the calendar and the mini calendar.

## Branches and commits

- Work happens issue by issue. Branch from `main` as `<type>/<issue>-<slug>`, e.g. `feat/28-mini-calendar` or `docs/12-readme`.
- Commits follow [Conventional Commits](https://www.conventionalcommits.org/) with the package as scope: `feat(react): …`, `fix(core): …`, `docs: …`, `ci: …`, `chore: …`.
- Commit only the files that belong to the change. Stage paths explicitly instead of `git add -A`.
- Open a pull request to `main` that links its issue (`Closes #N`). The maintainer reviews and merges.

## Pull request checklist

- [ ] `pnpm run typecheck`, `pnpm run lint` and `pnpm run test` pass.
- [ ] `pnpm run build` passes if packaging, entries or styles changed, and the packed check above is done.
- [ ] New or changed exports have English TSDoc with a one-line description (and an example when useful).
- [ ] Public optional props are typed `foo?: T | undefined`.
- [ ] Components use only `uc-*` tokens. No palette colors, no `dark:` variants, no visual styles inline.
- [ ] ARIA semantics, focus handling and screen-reader labels are kept (and translatable through `labels`).
- [ ] The README is updated for user-visible changes.
- [ ] Breaking changes are called out: a changed signature or prop, a removed export, or a renamed `classNames` slot, CSS variable, `labels` key or default shortcut.

## Adding a framework adapter

A new framework (e.g. Angular) gets its own package and must not require changes to another adapter.

1. Create `packages/<framework>/` named `@usecalendar/<framework>`, with `@usecalendar/core` as a `workspace:*` dependency and the framework as a peer dependency.
2. Copy the React package's build setup: tsup with `format: ["esm", "cjs"]`, `dts`, `platform: "neutral"`, an `exports` map with `types` first, `sideEffects` listing only the stylesheets, and the framework's client directive if it has one.
3. Render the core models (`visibleDays`, `monthWeeks`, `layoutWeek`, `layoutDay`, `nextFocus`, `nextMonthFocus`, `nextStripFocus`, `resolveKeymap`, …) with the framework's idioms. If you need logic the React adapter also has, move it to core first.
4. Reuse the `--uc-*` tokens and the same `classNames` slot names, `labels` keys and keyboard behavior, so apps can switch frameworks without restyling or retranslating.
5. Add the package to the README's packages table.

## Releases

Packages follow [Semantic Versioning](https://semver.org/) and are versioned independently. Publishing to npm happens only through the GitHub Actions workflow (`.github/workflows/publish.yml`) when a GitHub Release is published. Never run `npm publish` or `pnpm publish` locally. Changesets-based versioning is being set up in [#13](https://github.com/SebastianUrdaneguiBisalaya/usecalendar/issues/13). Until then, note user-visible changes under "Unreleased" in [CHANGELOG.md](./CHANGELOG.md).
