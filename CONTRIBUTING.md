# Contributing to usecalendar

Thanks for helping. This guide covers the setup, the day-to-day workflow and what a pull request needs. The engineering standards (TypeScript, styling contract, accessibility, versioning) are in [AGENTS.md](./AGENTS.md). Please read them before a non-trivial change.

## Setup

Requirements:

- Node.js 20 or newer (CI uses Node 24).
- pnpm 12.3.4, the version pinned in `devEngines` (`corepack enable` picks it up).

```bash
git clone https://github.com/SebastianUrdaneguiBisalaya/usecalendar.git
cd usecalendar
pnpm install   # also installs the git hooks (husky)
```

## Monorepo layout

```
packages/
  core/    @usecalendar/core: framework-agnostic types and calendar math (no UI, no runtime dependencies)
    src/index.ts        the package's only public entry
    tests/              vitest, mirroring src/
  react/   @usecalendar/react: React components and hooks, built on core
    src/index.ts        → "@usecalendar/react"
    src/mini/index.ts   → "@usecalendar/react/mini" (the day strip only)
    src/styles/         theme.css (Tailwind v4 apps) and index.css (→ styles.css, apps without Tailwind)
    tests/              vitest: SSR markup tests and jsdom hook/interaction tests
apps/
  storybook/  @usecalendar/storybook: private Storybook for reviewing the UI by hand (never published)
```

- Only the entry files (`src/index.ts`, and `src/mini/index.ts` in React) decide the public API. Anything they don't re-export is internal and can be refactored freely.
- Logic needed by more than one framework adapter belongs in core.
- `dist/` is generated by the build and never committed.

## Scripts

Run them from the repository root. Each one runs in every package.

| Command | What it does |
|---|---|
| `pnpm run build` | Builds every package with tsup (ESM, CJS and `.d.ts`), plus the React stylesheets. |
| `pnpm run dev` | Rebuilds on change (`tsup --watch`). In `packages/react`, `pnpm run dev:css` watches `styles.css`. |
| `pnpm run typecheck` | `tsc --noEmit` in every package. |
| `pnpm run lint` | Biome lint and format check. `pnpm run lint:fix` applies fixes. |
| `pnpm run test` | Vitest in every package. `pnpm run test:watch` for watch mode. |
| `pnpm run storybook` | Starts the Storybook at http://localhost:6006 to review the components by hand (see below). |
| `pnpm run smoke:pack` | Packs and installs both packages in a throwaway project and checks them (see below). Needs a build. |
| `pnpm changeset` | Adds a changeset describing your change for the next release. |

Tests never use a browser: no Playwright, Puppeteer or screenshot tests. React components are checked as server-rendered HTML (`react-dom/server`). Hook and interaction tests opt into jsdom with `// @vitest-environment jsdom`, and the `renderHook` helper is in `packages/react/tests/render-hook.tsx`. The UI itself is verified by hand, in the Storybook.

## Workflow after a source change

1. Write or update tests next to the change (`tests/` mirrors `src/`).
2. Run `pnpm run lint:fix`, then `pnpm run typecheck` and `pnpm run test`.
3. If you touched packaging, entry points or styles, run `pnpm run build` and `pnpm run smoke:pack`.
4. If the change is visible, review it in the Storybook (`pnpm run storybook`) and add or update the stories for new props, states or looks.
5. If the change is visible to consumers, update the README and the TSDoc of every affected export, and add a changeset (`pnpm changeset`).

Git hooks run some of this for you. **pre-commit** runs Biome on the staged files. **pre-push** runs `typecheck`, `test` and `build`. The hooks are a safety net, not a substitute for running the checks.

## Reviewing the UI in Storybook

`pnpm run storybook` starts the private Storybook in `apps/storybook` on port 6006. Stories import the packages' source, so edits hot-reload without a build. Use the toolbar to switch the theme (system, light, dark), `locale`, `timeZone`, `weekStart`, and the stylesheet: `theme.css` in a Tailwind v4 app, or the prebuilt `styles.css` of an app without Tailwind. The calendar stories keep events in state, so creating, moving and resizing really work, and every callback shows in the Actions panel. The Accessibility panel runs axe on demand.

Storybook is for manual review only. It is never published or deployed, and it has no test addons (no `@storybook/addon-vitest`, Playwright, Chromatic or screenshots). See [apps/storybook/README.md](./apps/storybook/README.md).

## Checking the packed packages

`pnpm run smoke:pack` tests the real tarballs the way consumers install them. Run `pnpm run build` first. It packs both packages, installs them with React in a throwaway project outside the repo, and checks that:

- `import` (ESM) and `require` (CJS) of `@usecalendar/core`, `@usecalendar/react` and `@usecalendar/react/mini` work.
- A `CalendarLocaleProvider` from `@usecalendar/react` applies to a `MiniCalendar` from `/mini` (the entries share their React contexts).
- Every React bundle starts with `"use client"`.
- `styles.css` contains the components' utilities, and `theme.css` registers them with `@source`.
- Types resolve from ESM (`.mts`) and CommonJS (`.cts`) files under `moduleResolution: "nodenext"`.

The publish workflow runs it before every release. Run it yourself after changing entries, `exports`, the tsup config or the styles. `pnpm run smoke:pack -- --keep` keeps the temporary project for inspection.

## Branches and commits

- Work happens issue by issue. Branch from `main` as `<type>/<issue>-<slug>`, e.g. `feat/28-mini-calendar` or `docs/12-readme`.
- Commits follow [Conventional Commits](https://www.conventionalcommits.org/) with the package as scope: `feat(react): …`, `fix(core): …`, `docs: …`, `ci: …`, `chore: …`.
- Commit only the files that belong to the change. Stage paths explicitly instead of `git add -A`.
- Open a pull request to `main` that links its issue (`Closes #N`). The maintainer reviews and merges.

## Pull request checklist

- [ ] `pnpm run typecheck`, `pnpm run lint` and `pnpm run test` pass.
- [ ] `pnpm run build` and `pnpm run smoke:pack` pass if packaging, entries or styles changed.
- [ ] A changeset is included if a published package changes for consumers.
- [ ] New or changed exports have English TSDoc with a one-line description (and an example when useful).
- [ ] Public optional props are typed `foo?: T | undefined`.
- [ ] Components use only `uc-*` tokens. No palette colors, no `dark:` variants, no visual styles inline.
- [ ] ARIA semantics, focus handling and screen-reader labels are kept (and translatable through `labels`).
- [ ] The README is updated for user-visible changes.
- [ ] Breaking changes are called out: a changed signature or prop, a removed export, or a renamed `classNames` slot, CSS variable, `labels` key or default shortcut.

## Adding a framework adapter

A new framework (e.g. Angular) gets its own package and must not require changes to another adapter.

1. Create `packages/<framework>/` named `@usecalendar/<framework>`, with `@usecalendar/core` as a `workspace:*` dependency and the framework as a peer dependency.
2. Copy the React package's build setup: tsup with `format: ["esm", "cjs"]`, `dts`, `platform: "neutral"`, an `exports` map with `types` first, `sideEffects` listing only the stylesheets, and the framework's client directive if it has one.
3. Render the core models (`visibleDays`, `monthWeeks`, `layoutWeek`, `layoutDay`, `nextFocus`, `nextMonthFocus`, `nextStripFocus`, `resolveKeymap`, …) with the framework's idioms. If you need logic the React adapter also has, move it to core first.
4. Reuse the `--uc-*` tokens and the same `classNames` slot names, `labels` keys and keyboard behavior, so apps can switch frameworks without restyling or retranslating.
5. Add the package to the README's packages table.

## Changesets

Each package is versioned independently with [changesets](https://github.com/changesets/changesets), following [Semantic Versioning](https://semver.org/):

```bash
pnpm changeset   # pick the packages, the bump (major / minor / patch) and write a summary for consumers
```

Commit the generated `.changeset/*.md` file with your change. The summary becomes the changelog entry, so write it for people using the package. Tests, tooling and docs outside the packages don't need a changeset.

A breaking change is a `major` bump: a changed signature or prop, a removed export, or a renamed `classNames` slot, CSS variable, `labels` key or default shortcut. Releasing `@usecalendar/core` also patch-bumps `@usecalendar/react`, because the React package depends on the exact core version it was released with.

## Releases

Only the maintainer releases, and only through GitHub Actions. Never run `npm publish` or `pnpm publish` locally.

1. On a branch, run `pnpm run version-packages`. Changesets consumes the pending changesets, bumps each package's `version` and updates its `CHANGELOG.md`.
2. Open a pull request with those changes and merge it to `main`.
3. Publish a [GitHub Release](https://github.com/SebastianUrdaneguiBisalaya/usecalendar/releases/new) (e.g. tag `@usecalendar/react@0.2.0`, with the changelog entries as notes).
4. `.github/workflows/publish.yml` runs typecheck → lint → test → build → smoke check, then publishes every package whose version isn't on npm yet (core first), with npm provenance.

The workflow needs the `NPM_TOKEN` repository secret: an npm automation token with publish rights on the `@usecalendar` scope.
