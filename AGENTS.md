# AGENTS.md

Standards and best practices for building, maintaining, and publishing **usecalendar**: a UI calendar library (Google Calendar-style month, week and day views) written in TypeScript, bundled with `tsup`, and distributed on npm as a framework-agnostic core plus framework adapters.

Sections 1-10 are the general engineering rules for this repo. The final section, "Project context: usecalendar", describes what this specific library is, where its code comes from, and the design rules that every package must follow. Read both before making non-trivial changes.

## 1. Project structure

```
packages/
  core/                # @usecalendar/core — framework-agnostic types and calendar math
    src/
      index.ts         # single public entry point (barrel file)
      ...              # internal modules, not exported directly
    tests/             # vitest tests, mirroring the structure of src/
  react/               # @usecalendar/react — React components and hooks (built on core)
    src/
    tests/
dist/                  # generated by tsup inside each package, never versioned
```

- Each package's `src/index.ts` is the **only** file that decides that package's public surface. Anything meant to be consumable from outside must be explicitly re-exported there (`export { Foo } from "./foo"`, `export type { FooOptions } from "./foo"`).
- Anything inside `src/` that doesn't pass through `index.ts` is not public API: it can be freely refactored without being a breaking change.
- Don't use `export *` on large internal modules: prefer explicit named exports to control exactly what gets frozen as the public contract.

## 2. TypeScript

- `strict: true` always. Don't relax type-checking rules just to "make it compile".
- Every public type, interface, or function must be exported from `src/index.ts` with `export type` / `export` as appropriate (`verbatimModuleSyntax` in this project enforces this explicit distinction).
- Exported types should be documented with TSDoc (`/** ... */`) in **English**, especially component props, hook options and callback parameters — these comments become the autocomplete/hover text consumers will see.
- Don't use `any` on the public surface. If an external type is unknown, use `unknown` (or a generic parameter, e.g. `CalendarEvent<TData>`) and force explicit narrowing.
- Prefer `type` over `interface` unless declaration merging or extended inheritance is needed; be consistent across the repo.
- **No object-oriented `class` usage anywhere in `src/`.** Model the domain with `type`/`interface` and implement behavior with arrow functions or classic (`function`) declarations. State lives in closures, plain objects, or React state/hooks. No inheritance, no `this`-based method binding, no abstract classes/decorators. The one exception is error types, which must extend `Error` so consumers can use `instanceof`.
- React components are function components. Don't use class components or `React.Component`.

## 3. Bundling with tsup (ESM + CJS + types)

Every package must be consumable both with `import` and with `require`:

```ts
import { Calendar } from "@usecalendar/react";
```
```js
const { Calendar } = require("@usecalendar/react");
```

This is achieved by:

- `tsup.config.ts` compiling to `format: ["esm", "cjs"]`, with `dts: true` (or `{ resolve: true }`) to generate the `.d.ts` files for each format, and `platform: "neutral"` (these packages run in browsers, not only Node).
- `package.json` with an explicit `exports` field per subpath, specifying `types`, `import`, and `require` — Node.js and modern bundlers resolve via `exports`, not `main`/`module` (those fields are kept only as fallback for older tooling).
- Key order inside each `exports` condition matters: `types` always first, then `import`/`require`.
- Never commit `dist/`. It's generated during CI/build and published via `files` in `package.json`.
- Framework adapter packages (e.g. `@usecalendar/react`) must keep the `"use client"` directive at the top of their output so they work in React Server Components frameworks (Next.js App Router).

### Checklist before publishing

1. `pnpm run build` generates `dist/index.mjs`, `dist/index.cjs` and the `.d.ts` files for every package with no errors.
2. `pnpm run typecheck` (`tsc --noEmit`) passes clean.
3. `pnpm run lint` (biome) passes clean.
4. `pnpm run test` passes.
5. Test the packed packages locally before the first real publish:
   ```bash
   pnpm --filter ./packages/core pack
   pnpm --filter ./packages/react pack
   # in another test project:
   npm install /path/to/usecalendar-core-x.y.z.tgz /path/to/usecalendar-react-x.y.z.tgz
   ```
   Verify that both `import` (ESM) and `require` (CJS) work, and that types resolve correctly in the editor.
6. **Publishing to npm must never be run manually or by an AI agent.** This project publishes exclusively through the GitHub Actions workflow at `.github/workflows/publish.yml`. Never run `npm publish` / `pnpm publish` from a local machine or from an agent session — it's a public, irreversible action, and doing it outside CI skips the required typecheck/lint/test/build gate.

### CI publish flow (`.github/workflows/publish.yml`)

- **Trigger**: a GitHub Release being published (`release: types: [published]`). Merging to `main` does **not** publish anything by itself — publishing is a separate, deliberate step: bump `version` (following semver, see section 4), merge that to `main`, then create a GitHub Release to trigger the actual npm publish.
- **Gate**: `typecheck` → `lint` → `test` → `build` must all pass before publishing is attempted.
- **Version guard**: before publishing, the workflow checks `npm view <name>@<version>` and skips the publish step if that version is already on the registry.
- **Required GitHub secret**: `NPM_TOKEN` (an npm **Automation** token with publish permission on the `@usecalendar` scope), configured in repository → **Settings** → **Secrets and variables** → **Actions**. Never commit this token or print it in workflow logs.
- The workflow publishes with `--provenance`, which requires `permissions: id-token: write`.
- The `if: ${{ !github.event.repository.fork }}` guard prevents the workflow from publishing from a fork.

## 4. Versioning and changes

- Follow [Semantic Versioning](https://semver.org/): `MAJOR.MINOR.PATCH`.
  - `MAJOR`: breaks the public API (changes an exported signature or a component prop, removes an export, changes documented behavior).
  - `MINOR`: new backwards-compatible functionality (a new optional prop, a new callback, a new export).
  - `PATCH`: backwards-compatible fixes.
- Any change to a package's `src/index.ts` is, by definition, a change to the public surface: treat it with the same care as an API change, not as an internal detail.
- Renaming a `classNames` slot, a CSS variable, or a `labels` key is a breaking change too: consumers style and translate against those names.

## 5. Quality and CI

- Lint and format with `biome` (configured in `biome.json`).
- `.editorconfig` sets the baseline (indentation, charset, line endings, final newline) for files Biome doesn't format — Markdown, YAML/workflow files, etc.
- Tests with `vitest`, mirroring the structure of `src/` inside `tests/`.
- **No visual or browser tests.** Don't add Playwright, Puppeteer, or screenshot-based tests, and never install them. Unit tests cover the pure logic in `@usecalendar/core`; the UI is verified manually by the maintainer.
- Don't merge to `main` with `typecheck`, `lint`, or `test` failing.
- The `prepublishOnly` script must run `build` (and optionally `test`) to avoid publishing an outdated or broken package.
- **Git hooks via [husky](https://typicode.github.io/husky/)** run checks locally before code reaches CI (`prepare: "husky"` installs them on `pnpm install`). Hooks are a local safety net, not a substitute for CI.

## 6. General library best practices

- **Minimal runtime dependencies.** Every dependency added to `dependencies` is inherited by every consumer. Prefer platform APIs (`Intl`, `Temporal`, the HTML Popover API, native pointer events) before adding a package. The approved runtime dependencies are `clsx` and `tailwind-merge` in framework adapters; anything else must be discussed in an issue first.
- **Framework packages are `peerDependencies`.** `react`/`react-dom` are never bundled or listed in `dependencies`.
- **Version ranges depend on who installs the dependency:**
  - `devDependencies` (and the root `package.json`) are **pinned to an exact version**: always `pnpm add -D -E <package>`. They only run in this repo, so builds stay reproducible.
  - Published runtime `dependencies` (e.g. `clsx`, `tailwind-merge`) use a **caret range** from the tested version: `pnpm add <package>` → `"^3.7.0"`. Consumers' package managers can then reuse a compatible copy the app already has instead of installing a duplicate. Reproducibility for this repo comes from `pnpm-lock.yaml`, which CI installs with `--frozen-lockfile`.
  - Internal workspace dependencies use `workspace:*`; pnpm replaces it with the exact version on publish, so `@usecalendar/react` always pairs with the `@usecalendar/core` it was released with.
  - `peerDependencies` (`react`, `react-dom`) use the widest range that is supported (`>=19.0.0`).
- **`sideEffects: false`** in `package.json` unless the package ships a stylesheet (list it in `sideEffects` then), to allow tree-shaking.
- Never log to `console` inside the library except behind an explicit debug flag controlled by the consumer.
- Don't throw generic exceptions (`throw new Error("something failed")`): define and export your own error types so the consumer can do `instanceof` and handle specific cases.
- Keep everything SSR-safe: never touch `window`, `document`, or the current time during render on the server. Values only known in the browser (today, now, element sizes) are read after mount.

## 7. Local development workflow

The exact sequence of commands to run after making a source change, how to try the built packages locally, and what to run before opening a pull request lives in [CONTRIBUTING.md](./CONTRIBUTING.md). Follow that instead of duplicating it here; update it there if the workflow changes.

## 8. Target environment

usecalendar is **client-side**: it renders UI in the browser (and server-renders in SSR frameworks). It holds no credentials or secrets, so server-only/secret-key rules don't apply. What does apply:

- Code must run in any modern browser and in SSR (Node) without crashing — no Node-only APIs (`fs`, `process`, `Buffer`) and no browser globals at module top level.
- Calendar data (events, titles) comes from the consumer's app; the library never fetches, stores, or sends it anywhere.

## 9. Monorepo layout: core + framework adapters

The repo is a `pnpm` workspace (`pnpm-workspace.yaml`):

```
packages/
  core/      # @usecalendar/core  — framework-agnostic types and calendar math, zero UI
  react/     # @usecalendar/react — React components and hooks, depends on core
  angular/   # (future) @usecalendar/angular — same pattern
```

- `@usecalendar/core` contains **no framework code**: no React, no DOM rendering, no JSX. Only types, constants and pure functions (date ranges, visible days, month/week layout, day layout, drag/resize math, keyboard focus model). Everything in core is unit-tested.
- Each framework adapter is its own npm package that depends on `@usecalendar/core` and renders it with that framework's idioms. Adding a new framework must never require changes to another adapter.
- If logic is needed by more than one adapter, it belongs in core.
- Version each package independently with [`changesets`](https://github.com/changesets/changesets).
- The publish gate from section 3 runs across the whole workspace (`pnpm -r run typecheck`, etc.).

## 10. Documentation website

- The repo doesn't ship a documentation website yet. If one is added later, put it in `apps/website/` (and add `apps/*` back to `pnpm-workspace.yaml`).
- The website must never be published to npm.
- Deploy the website independently of the npm release.

# Project context: usecalendar

## What it is

A drop-in, Google Calendar-style calendar for React apps (and other frameworks later): month view, week view, day view, an all-day lane, a current-time line, drag to create/move/resize, and full keyboard navigation. It is a **UI component, agnostic to business logic**: it shows the events it's given and reports user intent through callbacks. It never decides what an event is, how to save it, or what clicking does.

## Where the code comes from

The implementation is extracted from the maintainer's app **tempi** (local path `~/Documents/tempi`), where it already works in production:

| tempi source | usecalendar destination |
|---|---|
| `packages/core/src/domain/calendar-view.ts` | `@usecalendar/core` — views, visible days, navigation steps |
| `packages/core/src/domain/month-layout.ts` | `@usecalendar/core` — month weeks, week numbers, multi-day lanes |
| `packages/core/src/domain/day-layout.ts`, `reschedule.ts` | `@usecalendar/core` — time-grid layout, drag/resize math |
| `apps/web/src/features/calendar/components/time-grid/grid-focus.ts` | `@usecalendar/core` — keyboard focus model |
| `apps/web/src/features/calendar/components/month-grid/*` | `@usecalendar/react` — `MonthView` |
| `apps/web/src/features/calendar/components/time-grid/*`, `hooks/use-time-grid-drag.ts` | `@usecalendar/react` — `TimeGridView` |
| `apps/web/src/features/calendar/components/{event-chip.tsx,event-style.ts}` | `@usecalendar/react` — event rendering and styles |
| `apps/web/src/features/calendar/components/calendar-navigation-provider.tsx` | `@usecalendar/react` — `useCalendar` |

Port behavior and visuals faithfully; replace every tempi-specific dependency with props:

- tempi data hooks (`useEvents`, `useCalendars`, `useSettings`, `useTimeZone`) → `events`, `timeZone`, `weekStart`, `showWeekends`, … props, plus `onRangeChange` so apps can fetch events themselves.
- tempi actions (`useEventPanel`, `useRescheduleEvent`, `EventContextMenu`, recurrence scope dialogs) → callbacks (`onEventClick`, `onEventChange`, `onSlotClick`, `onDayClick`, …) and render props (`renderEvent`, `renderEventWrapper`).
- `react-i18next` → `locale`, `labels` and `formatters` props, with formatting through `Intl`.
- shadcn/Base UI components (`Popover`, `Button`, `Badge`) and `lucide-react` → plain elements, the native HTML Popover API, and inline SVG.
- tempi's zod schemas, repositories and recurrence engine are **not** ported: consumers pass already-expanded occurrences.

## Design rules

- **Props over app state.** Every behavior is controllable: stateful props come in controlled (`view` + `onViewChange`) and uncontrolled (`defaultView`) forms.
- **Generic event data.** The public event type is `CalendarEvent<TData>`; callbacks hand back the consumer's own `data` untouched.
- **Styling contract.**
  - Components are styled with Tailwind CSS v4 utility classes written as full literal strings (never built dynamically, or Tailwind can't detect them).
  - `@usecalendar/react` ships two stylesheets built from `packages/react/src/styles/`:
    - `theme.css` for Tailwind v4 apps (`@import "@usecalendar/react/theme.css"`): tokens + `@theme` mapping + `@source` of the compiled components.
    - `styles.css` for apps without Tailwind: prebuilt utilities + tokens, **without** Tailwind's preflight so it never resets the host page.
  - Every component accepts `className` (root) and `classNames` (per-part slots), merged with `cn()` (`clsx` + `tailwind-merge`) so consumer classes always win.
  - Colors and radius come only from the `--uc-*` tokens, exposed as `uc-*` Tailwind colors (`bg-uc-background`, `text-uc-muted-foreground`, `rounded-uc`, …). Never hard-code palette colors (`bg-white`, `text-zinc-500`) in components.
  - Each token falls back to the matching shadcn token (`--background`, `--primary`, …), so the calendar matches a shadcn app, including its dark mode, with zero config.
  - **Dark mode lives in the tokens, not in `dark:` variants.** `theme.css` switches the tokens on `.dark` / `[data-theme="dark"]`, or on the OS preference unless `.light` / `[data-theme="light"]` opts out. Components must not use `dark:` utilities and the library must not define `@custom-variant dark`, which would override the host's.
  - **No visual styles in inline `style`.** Inline styles beat every class, so consumers couldn't override them without `!important`. Components set only data (`--uc-event-color`, positions/sizes computed at runtime) inline. Look-and-feel (fills, stripes, muting) lives in `theme.css` rules inside `@layer components`, driven by `--uc-*` variables (e.g. `--uc-event-tint`), so any utility class wins over them. Defaults for those variables go in `@layer base` so any unlayered consumer rule wins.
  - Fonts are inherited from the host app.
- **Accessibility is part of the port.** Keep tempi's ARIA grid semantics, roving focus, keyboard shortcuts and screen-reader labels.
- **Time.** Dates use the global `Temporal` API (`Temporal.PlainDate`, `Temporal.ZonedDateTime`); event times are ISO 8601 instants with an offset, always compared by time (`Date.parse` / `Temporal.Instant.compare`), never as text. No polyfill is bundled or imported from `src/`; the README documents loading `temporal-polyfill/global` on runtimes without native `Temporal` (Node 24 included). Tests load it through each package's vitest `setupFiles` (`tests/setup.ts`), with `temporal-polyfill` as a devDependency only.

## Documentation for consumers

- `README.md` (English) must include installation, Tailwind setup, a quick start, every component's props, callback recipes (create/move/resize, context menus, fetching by visible range), theming, localization, and accessibility notes.
- Every exported component, hook, type and function has TSDoc in English with a one-line description and, when useful, an example.
